## 문제 상황

목록 화면의 페이지 상태를 URL로 관리하고 있다. `?page=2` 같은 형태고, 새로고침이나 링크 공유를 위해 컴포넌트 state가 아니라 URL을 단일 진실 원천으로 쓴다.

page size가 10이고 데이터가 11개면 2페이지에는 1개가 보인다. 그 상태에서 그 1개를 삭제하면 전체 데이터는 10개, 즉 페이지는 1개뿐인데 **URL은 여전히 `?page=2`를 가리키고 있다.** 서버는 범위 밖 페이지에 대해 빈 배열을 돌려주고, 화면에는 아무것도 없는 표가 남는다.

이걸 이렇게 고쳤다.

```tsx
useEffect(() => {
  if (items.length === 0) {
    setPage(page - 1);
  }
}, [items]);
```

동작은 한다. 삭제하면 빈 화면이 잠깐 스쳤다가 1페이지로 돌아온다. 그런데 이 방식은 **증상을 조건으로 착각하고 있다.**

## 원인 분석

문제의 실제 조건은 `items.length === 0`이 아니라 **`page > 마지막 페이지`** 다. 빈 배열은 그 조건이 만들어낸 여러 결과 중 하나일 뿐이고, 다른 원인으로도 똑같이 만들어진다. 이 방식의 약점은 전부 여기서 파생된다.

**첫째, 정당한 빈 결과와 구분되지 않는다.** 검색어를 입력했는데 결과가 0건인 상황도 `items.length === 0`이다. 데이터가 아예 없는 신규 사용자의 1페이지도 0이다. 위 코드는 이 경우 `page`를 0으로 만든다. 그래서 `page > 1` 가드가 필요해지는데, 이 가드가 필요하다는 사실 자체가 조건을 잘못 잡았다는 신호다. 범위 검사로 짜면 데이터가 0건일 때 마지막 페이지가 1이고 현재 페이지도 1이라 애초에 발동하지 않는다.

**둘째, 얼마나 벗어났는지 모른다.** 빈 배열에는 "몇 페이지 초과인지"에 대한 정보가 없다. 그래서 한 칸씩만 뒤로 갈 수 있다. 데이터 21개(3페이지)에서 체크박스로 11개를 한 번에 지우면 남는 건 1페이지뿐인데, 3 → 2 → 1로 두 번 왕복한다. **요청 두 번, 빈 화면 두 번이다.**

**셋째, 로딩 중의 빈 배열에도 반응한다.** 페이지를 옮기는 동안 `items`가 잠깐 `[]`가 되는 구현이라면(placeholder 없이 새로 fetch하는 경우) 응답이 오기도 전에 이전 페이지로 되돌아간다. 그러면 다시 fetch가 돌고, 운이 나쁘면 왕복이 반복된다.

**넷째, `push`로 URL을 바꾸면 뒤로가기가 막힌다.** 이게 가장 실질적인 함정이다. `?page=2`가 히스토리에 남은 채로 1페이지에 와 있으면, 사용자가 뒤로가기를 눌러 2페이지로 돌아가고, 거기서 effect가 다시 발동해 1페이지로 밀어낸다. **뒤로가기로 이 화면을 벗어날 수 없게 된다.**

## 해결 방법

서버 응답에 `total`(또는 `totalPages`)이 있으면 그걸로 범위를 직접 검사한다. 페이지네이션 UI에 마지막 페이지 번호나 "전체 N건"이 찍히고 있다면 이미 내려오고 있는 값이다.

```tsx
const lastPage = Math.max(1, Math.ceil(total / pageSize));

useEffect(() => {
  if (page > lastPage) {
    // 몇 페이지가 날아가든 한 번에 도달한다
    router.replace({ query: { ...query, page: lastPage } });
  }
}, [page, lastPage]);
```

`items`를 보지 않기 때문에 빈 검색 결과와 혼동되지 않고, `page > 1` 가드도 필요 없다. 21개에서 11개를 지운 경우도 3 → 1로 한 번에 간다.

주의할 점은 **비어서 돌아온 바로 그 응답의 `total`을 써야 한다**는 것이다. 캐시에 남아 있던 이전 `total`로 계산하면 아직 3페이지가 있다고 판단해서 보정이 안 된다.

`total`을 안 주는 API라면 그때만 빈 배열을 폴백으로 쓴다. 대신 가드 세 개가 전부 필요하다.

```tsx
useEffect(() => {
  if (!isSuccess) return;          // 로딩·에러 상태의 빈 배열 제외
  if (isPlaceholderData) return;   // 이전 페이지 데이터를 보여주는 중이면 제외
  if (items.length === 0 && page > 1) {
    router.replace({ query: { ...query, page: page - 1 } });
  }
}, [isSuccess, isPlaceholderData, items, page]);
```

그리고 어느 쪽이든 `push`가 아니라 **`replace`** 다. 잘못된 페이지는 히스토리에 남길 이유가 없다.

### 애초에 벗어나지 않게 하는 쪽

보정은 그물이고, 더 나은 건 범위를 벗어나는 상태를 만들지 않는 것이다.

삭제 시점에는 "이게 이 페이지의 마지막 한 건인지"를 이미 알고 있다. 무효화 전에 URL을 먼저 고치면 빈 화면이 아예 그려지지 않는다.

```tsx
const { mutate } = useMutation({
  mutationFn: deleteRow,
  onSuccess: () => {
    if (items.length === 1 && page > 1) {
      router.replace({ query: { ...query, page: page - 1 } });
    }
    queryClient.invalidateQueries({ queryKey: ['rows'] });
  },
});
```

같은 종류의 문제가 삭제 말고도 있다. **필터·정렬·page size를 바꿀 때 `page`를 1로 같이 리셋하지 않으면** 3페이지에 있는 상태에서 결과 2건짜리 필터를 걸었을 때 3 → 2 → 1로 걸어 내려간다. 낭비되는 fetch가 두 번이고, 겉보기에는 잘 동작하는 것처럼 보인다. URL 상태를 바꾸는 지점마다 페이지를 함께 다뤄야 한다는 뜻이고, 이게 "비면 되돌린다"가 잘못된 레이어인 이유다.

## 왜 이 방법인가

**`items.length === 0` 방식이 아예 틀린 건 아니다.** `total`을 주지 않는 API를 상대할 때는 클라이언트가 가진 유일한 정보가 빈 배열뿐이다. 최후의 그물로는 쓸 만하다. 다만 주 메커니즘으로 쓰기엔 조건이 부정확하고, 위의 가드 없이 쓰면 0페이지로 가거나 뒤로가기가 막힌다.

**서버에서 클램프하는 방법**도 있다. 범위를 넘는 `page`를 받으면 마지막 페이지 데이터를 돌려주는 식이다. 클라이언트가 신경 쓸 게 없어지지만 URL과 실제로 보는 내용이 어긋나고(URL은 `page=2`인데 1페이지 내용), 공유된 링크의 의미가 시점에 따라 달라진다. API를 우리가 통제할 수 있어도 나는 이 쪽을 안 골랐다.

**1페이지가 0건인 건 고칠 대상이 아니다.** 이건 정상적인 빈 상태이고 "등록된 항목이 없습니다" 같은 UI가 필요한 자리다. `page > 1` 가드는 방어 코드가 아니라 이 구분을 지키는 코드다.

## 정리

- 빈 페이지의 조건은 `items.length === 0`이 아니라 **`page > lastPage`** 다. 증상 말고 조건을 검사한다
- `total`이 있으면 `Math.max(1, Math.ceil(total / pageSize))`로 클램프한다. 몇 페이지가 날아가도 이동 한 번이고, 빈 검색 결과와 헷갈리지 않는다
- 클램프에 쓰는 `total`은 **비어서 돌아온 그 응답의 값**이어야 한다. 캐시된 이전 값이면 보정이 안 된다
- 빈 배열 폴백을 쓸 거면 가드 세 개(성공 상태 / placeholder 아님 / `page > 1`)를 전부 건다
- URL 보정은 반드시 **`replace`**. `push`면 뒤로가기 → 빈 페이지 → 다시 밀려남으로 화면에 갇힌다
- 삭제 `onSuccess`에서 미리 페이지를 내리면 빈 화면이 그려지지 않는다. 필터·정렬·page size 변경 때도 `page`를 1로 같이 리셋한다
