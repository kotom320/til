## 배경

시간마다 도는 PR 리뷰 자동화를 쓰고 있다. 리뷰 코멘트에 사람이 대댓글로 "이건 의도된 겁니다"라고 물리면, 봇이 그걸 **다음 리뷰에 적용 가능한 규칙**으로 바꿔 `knowledge/<레포명>.md`에 적어두는 구조다.

```
knowledge/
├── _공통.md                  레포 공통 규칙
└── <레포명>.md               레포별 규칙
    ## 아키텍처 / 관례
    ## 지적하지 말 것          ← 대댓글 학습의 목적지
    ## 자주 놓치는 것
```

리뷰 품질은 괜찮아 보였다. 그런데 **이 지식이 실제로 다음 리뷰에 반영되고 있는지는 확인해 본 적이 없었다.** 잘 되는 것 같다는 인상만 있었다.

## 확인해 보니

리뷰 프롬프트가 기각 사유를 네 값 중 하나로 시작하라고 강제하고 있었다. `근거 확인 불가` / `지식: 지적하지 말 것` / `중복` / `확신 부족`. 즉 **"지식 때문에 지적을 접었다"가 로그에 남게 이미 설계돼 있었다.** 쿼리를 안 돌렸을 뿐이다.

28일치 실행 로그 48건을 집계했다.

```
실제 기각 83건의 사유 분포
  근거 확인 불가   26  (31.3%)
  중복           24  (28.9%)
  확신 부족       20  (24.1%)
  규정 외 서술     11  (13.3%)
  지식            2  ( 2.4%)   ← 두 건
```

2.4%. 첫 반응은 "지식이 안 쓰이고 있구나"였는데, 이 숫자는 그렇게 읽으면 안 되는 숫자였다.

## 왜 이 숫자로는 판단할 수 없나

### 계측에 사각지대가 있다

프롬프트는 "`지적하지 말 것`에 걸리는 항목은 게시하지 않는다"이다. 모델이 **생성 단계에서 걸러버리면 그건 애초에 finding이 되지 않아서 기각 테이블에 오르지 않는다.**

그래서 2.4%는 두 가지와 똑같이 부합한다.

- 지식이 장식이고 아무 영향을 안 준다
- 지식이 잘 들어서 발견되기 전에 눌렀다

**둘을 구분할 데이터가 로그에 없다.** 이게 진짜 결함이었다. 수치가 낮은 게 문제가 아니라 수치를 해석할 수 없는 게 문제다.

### 지식의 3분의 1만 계측 대상이었다

섹션별로 항목을 세어 보니 이랬다.

| 섹션 | 항목 수 | 로그 계측 |
|---|---|---|
| `지적하지 말 것` | 15 | 있음 (`기각 사유: 지식`) |
| `자주 놓치는 것` | 32 | **없음** |
| `아키텍처 / 관례` | 0 | 없음 |

가장 큰 섹션인 `자주 놓치는 것`은 **지적을 줄이는 게 아니라 제대로 찾게 만드는 지식**인데, 이게 쓰였는지는 어디에도 안 남는다. 정확한 진단은 "지식이 안 쓰인다"가 아니라 **"47개 중 15개만 측정 가능하고, 그 15개가 2.4%다"** 였다.

## 진짜 위험은 무시가 아니라 만료였다

여기서 방향이 바뀌었다. 원래 질문은 "지식이 읽히고 있나"였는데, 항목들을 실제로 읽어 보니 더 급한 게 있었다.

```markdown
- antd 는 4.24.8 이다 (2026-08-21 확인)
- OpenAPI 생성 스키마는 더 이상 git에 추적되지 않는다 (2026-08-06 확인)
- bodyStyle 은 antd v4 프롭이라 정상이다. v5 기준 deprecated 라고 지적하지 말 것
```

전부 의존성 하나 올리거나 설정 하나 바꾸면 거짓이 된다. 그리고 **`지적하지 말 것`의 항목이 틀리면 옳은 지적이 죽는다.**

이게 가정이 아니라는 증거가 저장소 안에 있었다.

> `PR CI 의 타입 검증은 워크플로마다 다르다` **(2026-08-31 정정.** 이전 「PR CI 는 타입 검증을 아예 하지 않는다」는 `analysis.yml` 만 보고 내린 판단이라 절반만 맞았다)

틀린 항목이 실제로 지식에 들어가 있었고, 나중에 정정됐다. 위험이 실증됐고 자정도 한 번 됐다.

### 세 섹션은 비용 구조가 반대다

| 섹션 | 하는 일 | 항목이 틀리면 | 심사 단계가 잡나 |
|---|---|---|---|
| `지적하지 말 것` | **억제** | **옳은 지적이 사라진다** | **못 잡는다** |
| `자주 놓치는 것` | 증폭 | 오탐이 하나 생긴다 | 잡는다 |

`자주 놓치는 것`이 틀리면 오탐이 하나 나오고, 그건 기존 심사(`근거 확인 불가` / `확신 부족`)가 걸러낸다. 실제로 28일간 46건이 그렇게 걸러졌다.

반면 **억제형 지식의 실패는 무음이다.** 억제된 지적은 생성되지 않으므로 기각표에도 로그에도 남지 않는다. 사후에 발견할 방법이 원리적으로 없다.

한 파일에 한 정책으로 섞여 있었는데, 정책이 달라야 하는 것이었다.

## 고친 것

### 1. 억제형 지식에만 재확인 기한

```markdown
- **`bodyStyle` 은 antd v4 프롭이라 정상이다.** v5 기준 deprecated 로 지적하지 말 것.
  <!-- 재확인: 2026-11-21 -->
```

기한이 지나면 봇이 그 실행에서 근거를 다시 확인하고 갱신하거나 정정한다. 확인 못 했으면 그렇게 로그에 남긴다.

**중요한 건 기한이 지나도 항목을 무시하지 않는다는 점이다.** 억제는 그대로 적용한다. 확인 없이 억제를 푸는 쪽이 동료 PR에 잘못된 지적을 남길 위험이 더 크기 때문이다. 기한의 목적은 자동 비활성화가 아니라 **재확인 강제**다.

### 2. 로그에 「참고한 지식」 표

```markdown
**참고한 지식**
| 파일 | 항목 (앞 30자 그대로) | 작용 |
|---|---|---|
| blue-web-byb-v2.md | `전역 QueryClient 기본값은 retry: false` | 지적 접음 |
| admin-v2.md | `bodyStyle 은 antd v4 프롭이라 정상이다` | 갱신 (package.json 4.24.8 확인) |
```

두 가지가 설계의 핵심이다.

- **원문 앞 30자를 그대로 옮기게 한다.** 요약하거나 바꿔 쓰면 나중에 어느 항목인지 매칭할 수 없다. 그리고 인용을 강제하면 안 읽고 지어내기가 어려워진다
- **걸린 게 없으면 `적용된 항목 없음`이라고 명시하게 한다.** 빈 표와 미적용은 다른 상태다. 이걸 구분하지 않으면 사각지대가 그대로 남는다

### 3. 집계 스크립트

```bash
python3 scripts/knowledge-report.py
```

항목별 적중 횟수, 한 번도 안 걸린 항목, 기한 경과 항목을 낸다. **모델을 검사하는 게 아니라 산출물이 스스로 보고하게 만드는 방식**이다.

돌려서 나온 기준선이 이랬다.

```
로그 49건 (지식 표 있음 0 / '적용된 항목 없음' 명시 0 / 표 자체 없음 49)
추적 항목 38개, 전부 적중 0
```

당연하다. 아직 표가 없으니까. 이게 "이전" 상태이고, 다음 주에 다시 돌리면 계측이 작동하는지가 이 숫자로 나온다.

## 곁가지로 알게 된 것

### 규모가 작으면 검색기를 붙이지 않는 게 맞다

"매번 지식을 다 읽으면 불필요한 정보까지 읽는 것 아닌가"가 원래 걱정이었다. 재보니 이랬다.

```
2026-08-03  항목 22   3,080 B
2026-08-24  항목 48  14,112 B
현재         항목 66  17,888 B
삭제된 항목: 0건
```

17.9KB면 5~6천 토큰이라 **비용 문제가 아니다.** 지금 있는 건 희석 문제고, 이 속도(28일에 3배, 삭제 0건)면 6개월 뒤에 둘 다가 된다.

그래서 지금 RAG나 임베딩 검색을 붙이는 건 손해다. 66항목짜리에 검색기를 붙이면 전체 읽기보다 정확도가 떨어지고 실패 모드만 늘어난다. **먼저 할 일은 검색기가 아니라 가지치기이고, 무엇을 지울지는 적중 카운터가 알려준다.** 계측이 성장 문제의 답이기도 했다.

### 솔깃한 아이디어를 데이터로 접었다

기각 83건 중 46건(55%)이 봇이 스스로 물린 것이었다. "같은 헛다리를 반복하면 그것도 지식으로 올리자"가 자연스러운데, 반복 여부를 재보니 **재발 클러스터가 1개뿐이고 그마저 같은 날 같은 PR의 같은 라인**이었다.

회수했으면 절대 안 걸리는 규칙 46개가 생겨서 희석만 심해졌을 것이다. 그리고 이 결과는 봇이 **매번 새로운 걸 의심했다가 근거를 못 찾아 접고 있다**는 뜻이라 오히려 정상 동작의 신호였다.

### 어휘가 새면 나중에 아무것도 못 잰다

기각 사유 83건 중 11건(13%)이 규정된 네 값으로 시작하지 않았다. 내용은 오히려 좋았다. `확인해 보니 문제가 아니었다`, `방어 코딩 제안이라 게시 기준 미달` 같은 것들.

그런데 흥미롭게도 **봇이 이 문제를 스스로 진단해 지식에 적어둔 상태였다.**

> `확신 부족`으로 뺀 건이 `APPROVE`를 막는다는 규칙에서 「확인해 보니 문제가 아니었다」는 제외한다. **로그의 기각 사유 어휘가 둘을 하나로 뭉뚱그리는데**, 승인을 막아야 하는 건 확인하지 못해서 뺀 것뿐이다.

어휘를 여섯 개로 늘리고 각각이 `APPROVE`를 막는지 표로 못박았다. `무해 확정`과 `범위 밖`이 새로 생겼다.

## 정리

- **"잘 되는 것 같다"와 "아무 일도 안 일어난다"는 계측 없이 구분되지 않는다.** 리뷰 품질이 좋아 보인 것과 지식이 쓰인 것은 별개 사실이었다
- 이미 만들어 둔 계측이 있는지 먼저 본다. **기각 사유 어휘가 이미 계측기였는데 28일간 쿼리를 안 돌렸다**
- 낮은 수치보다 **해석 불가능한 수치**가 더 나쁘다. 생성 단계에서 걸러진 건 흔적을 안 남기므로, 2.4%는 정반대 두 해석과 똑같이 부합했다
- **억제하는 지식과 증폭하는 지식은 정책이 달라야 한다.** 증폭은 틀려도 오탐 하나고 심사가 잡는다. 억제는 틀리면 옳은 지적이 무음으로 사라진다
- 억제형 항목에는 기한을 준다. 단 **기한이 지나도 자동으로 끄지 않는다.** 목적은 비활성화가 아니라 재확인 강제다
- 모델이 지식을 읽었는지 사후에 검사할 방법은 없다. **산출물이 스스로 보고하게 만든다.** 원문 인용을 강제하고, 적용이 없으면 "없음"을 명시하게 한다
- 지식 저장소는 삭제 없이 단조 증가한다(28일에 3배). **검색기를 붙이기 전에 적중 0 항목을 지운다.** 계측이 가지치기 기준을 준다
