## 문제 상황

UI 작업을 마친 뒤 "빌드 통과"로 끝내지 않고 실제 브라우저에서 확인하는 단계를 두고 있다. 이 단계를 Claude in Chrome(크롬 확장)으로 하고 있었는데, 방식 자체에 대한 지적이 나왔다.

확장은 내가 매일 쓰는 크롬에 붙는다. 사이트 단위로 권한을 주는 구조이긴 하지만, 권한을 준 순간부터 에이전트는 로그인된 실제 세션 안에서 움직인다. "그 안에서 무엇을 하는지 통제하기도, 나중에 확인하기도 어렵다"는 게 핵심이었다. 화면 하나 확인하겠다고 일상 브라우저 전체를 작업 대상으로 내주는 셈이다.

그래서 화면 검증 경로를 Playwright MCP로 옮겼다. 확장을 지운 게 아니라, QA 단계가 더 이상 그쪽을 거치지 않게 만든 것이다.

## 두 방식은 무엇이 다른가

| | Claude in Chrome | Playwright MCP |
|---|---|---|
| 브라우저 | 내가 쓰던 크롬에 확장으로 붙음 | `npx @playwright/mcp`가 띄우는 별도 Chromium |
| 프로필·세션 | 로그인된 실제 프로필 그대로 | 전용 `--user-data-dir` 로 격리 |
| 관측 범위 | 열려 있는 다른 탭까지 목록으로 조회 | 자기가 띄운 브라우저 안만 |
| 조작 방식 | 스크린샷 + 좌표 클릭 중심 | 접근성 트리의 ref로 요소 지목 |
| 종료 | 내 브라우저라 그대로 남음 | `browser_close`로 인스턴스째 종료 |
| 산출물 | 세션 안에 남음 | `--output-dir`에 파일로 떨어짐 |

권한 얘기를 빼고 봐도 조작 방식의 차이가 크다.

확장 쪽의 기본 흐름은 세션을 시작할 때 먼저 열린 탭 목록을 받아오고, `computer` 도구로 스크린샷을 찍어 좌표를 눌러가며 진행하는 것이다. 사람이 브라우저를 쓰는 방식에 가깝지만, 그 대가로 "지금 화면 어디를 눌렀는지"가 좌표로만 남는다.

Playwright MCP는 `browser_snapshot`으로 접근성 트리를 받고 거기서 얻은 ref로 `browser_click`을 한다. 좌표가 아니라 요소를 지목하므로 레이아웃이 조금 밀려도 같은 곳을 누른다. 간격이나 크기를 확인할 때도 눈대중 대신 `browser_evaluate`로 `getBoundingClientRect()`를 재면 된다.

```
// 눈으로 "괜찮아 보이는데" 대신
browser_evaluate: () => document.querySelector('.slide').getBoundingClientRect()
```

여기서 쓰는 조작 단위가 Playwright 테스트 코드와 같다는 점도 크다. 수동으로 확인한 시나리오가 반복 확인 대상이 되면 그대로 `*.spec.ts`로 옮길 여지가 있다. 확장 기반 검증은 그 경로가 없다.

## 옮긴 과정

**1. MCP 서버 등록** (`~/.claude.json`)

```json
{
  "mcpServers": {
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": [
        "-y", "@playwright/mcp@0.0.79",
        "--user-data-dir", "/Users/me/.claude-playwright-mcp/profile",
        "--output-dir", "/Users/me/.claude-playwright-mcp/output",
        "--viewport-size", "1440x900",
        "--sandbox"
      ]
    }
  }
}
```

버전을 `@0.0.79`로 고정한 이유는 도구 이름과 인자 형태가 버전마다 바뀌기 때문이다. 스킬 문서가 특정 도구 이름을 전제하고 있으면 latest로 두는 순간 문서와 실제가 어긋난다.

**2. 권한 허용** (`~/.claude/settings.json`)

```json
{ "permissions": { "allow": ["mcp__playwright"] } }
```

브라우저 조작마다 확인을 받으면 QA가 진행되지 않는다. 대신 이 허용이 열어주는 범위가 "격리된 프로필의 브라우저 하나"로 한정된다는 게 이번 변경의 요점이다.

**3. QA 스킬 작성**

검증 절차를 스킬로 고정했다. 요약하면 이렇다.

- dev 서버는 이미 떠 있으면 재사용한다. 아무 포트나 쓰지 않는다. 백엔드가 허용하지 않는 포트로 띄우면 페이지는 뜨는데 API가 전부 막혀서, 화면만 보고 로그인 문제로 오진하게 된다.
- "페이지가 뜬다"가 아니라 "X를 누르면 Y가 된다"를 확인한다.
- `browser_console_messages` 확인은 필수다. 화면이 멀쩡해 보여도 에러가 쌓이고 있을 수 있다.
- 스크린샷을 찍어 사용자에게 파일로 보여준다. "확인했습니다" 텍스트로 끝내지 않는다.
- 끝나면 `browser_close`.

**4. 딜리버리 파이프라인 연결**

이슈 접수부터 PR까지를 잇는 상위 스킬에서 QA 단계가 이 스킬을 가리키도록 했다. 화면에 닿는 작업은 테스트·빌드 통과만으로 다음 단계로 넘어가지 못한다.

## 왜 이 방법인가

가장 크게 잃는 건 로그인 세션이다. 격리된 프로필이니 당연히 아무 데도 로그인돼 있지 않다. 로그인이 필요한 화면은 로그인 페이지까지만 이동시켜 두고 사용자가 직접 로그인한다. 자격증명을 에이전트가 대신 입력하지 않는다.

그래서 프로필을 매번 버리는 임시 디렉터리로 두지 않고 `--user-data-dir`로 고정했다. 완전 휘발성으로 두면 확인할 때마다 로그인해야 해서 QA 자체를 안 하게 된다. 일상 브라우저와는 분리하되 같은 날 반복 확인에는 재로그인이 필요 없는 중간 지점이다.

확장 쪽이 편했던 이유가 정확히 이 지점이었다. 이미 로그인된 브라우저를 그대로 쓰니 준비가 필요 없다. 그 편의를 세션 격리와 맞바꾼 것이고, 로그인 한 번을 수동으로 하는 비용이 그보다 싸다고 봤다.

## 한계

프로필 격리는 자격증명 보호이지 프롬프트 인젝션 방어가 아니다. 페이지 콘텐츠에 지시문이 심어져 있으면 읽는 건 마찬가지다. 달라지는 건 그게 통했을 때 닿을 수 있는 범위다. 로그인된 메일·관리자 콘솔이 열린 브라우저냐, 방금 띄운 빈 프로필이냐의 차이다. "더 안전해졌다"보다 "잘못됐을 때 번지는 범위가 줄었다"가 정확한 표현이다.

확장 자체를 제거한 것도 아니다. 화면 검증이라는 반복 작업의 기본 경로를 바꾼 것뿐이라, 확장에 준 사이트 권한은 별도로 점검해야 한다.

## 정리

- 브라우저 자동화 도구를 고를 때 기능표보다 먼저 볼 것: **어느 브라우저의, 어느 세션에서 도는가.**
- Playwright MCP는 별도 프로필의 별도 인스턴스에서 돈다. 좌표가 아니라 접근성 트리 ref로 조작하고, 조작 단위가 테스트 코드와 같다.
- 대가는 로그인 세션 부재다. `--user-data-dir`로 프로필을 고정해 재로그인 비용만 줄여둔다.
- 격리는 인젝션 방어가 아니라 blast radius 축소다.
