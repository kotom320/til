## 배경

이미지 첨부 기능에서 아이폰으로 찍은 HEIC 사진이 변환되지 않는 버그를 잡느라 디코더를 `heic2any`에서 `libheif-js`로 교체했다. 문제는 잘 해결됐는데, 한참 뒤에 `libheif-js`의 라이선스가 **LGPL-3.0**이라는 걸 알았다.

그때까지 내가 라이선스에 대해 배운 건 이 정도였다.

> "쓰면 안 되는 라이선스가 있다. 그걸 쓰면 소유권을 주장하고 우리 코드에 직/간접적으로 영향력을 행사할 수 있다."

이 문장이 틀렸다는 것부터 시작해서, 며칠에 걸쳐 알게 된 것들을 정리한다.

## "소유권을 주장한다"는 틀렸다

카피레프트 라이선스는 **저작권을 가져가지 않는다.** 내 코드의 저작권은 100% 내 것으로 남는다.

실제 구조는 이렇다. 라이브러리 저작자가 "이 조건을 지키면 써도 된다"는 **조건부 사용 허락**을 준다. 조건을 어기면 벌어지는 일은 "상대가 내 코드를 소유하게 됨"이 아니라 **"허락이 소멸해서 내가 배포할 권리를 잃음"** 이다. 그러면 배포 자체가 저작권 침해가 되고, 구제 수단은 배포 중단 또는 준수다.

방향이 반대다. 내 것을 뺏기는 게 아니라 남의 것을 쓸 자격을 잃는 것이다. 그래서 해법도 항상 둘 중 하나다. **조건을 지키거나, 걷어내거나.**

## 판단 축 1: 배포(conveying)를 하는가

이게 제일 중요한데 놓치기 쉽다. GPL/LGPL 의무는 **사용**이 아니라 **배포**에 걸린다.

| 상황 | 의무 |
|---|---|
| 사내 내부용으로만 사용 | 없음 |
| 서버에 두고 API로만 제공 | 없음 (배포 아님) |
| **JS 번들을 브라우저로 전송** | **있음** |

세 번째가 프론트엔드의 함정이다. "우리 웹사이트일 뿐인데"라고 생각하지만 방문자 한 명 한 명이 사본을 받아간다. 법적으로 배포가 맞다.

그리고 두 번째(서버)의 구멍을 막으려고 만든 게 **AGPL**이다. 네트워크 너머 사용자도 배포 대상으로 본다. 백엔드에서 진짜 조심해야 할 건 GPL이 아니라 AGPL이다.

## 판단 축 2: 결합 범위

| 등급 | 라이선스 | 배포 제품에서 |
|---|---|---|
| 관대형 | MIT, BSD, ISC, Apache-2.0 | 자유. 고지문만 유지 |
| 파일 단위 카피레프트 | MPL-2.0, EPL | 사용 가능. **그 파일을 수정했을 때만** 수정분 공개 |
| 라이브러리 단위 카피레프트 | **LGPL-2.1 / 3.0** | 조건부. 교체 가능한 형태로 분리 배포 + 고지 |
| 전체 카피레프트 | **GPL-2.0 / 3.0** | 배포 제품에서는 피함 |
| 네트워크 카피레프트 | **AGPL-3.0** | 서버에서도 피함 |
| 오픈소스 아님 | SSPL, BUSL, Elastic, CC-BY-NC | 별도 검토 필수 |
| **라이선스 표기 없음** | | **최악. 기본값이 "all rights reserved"라 아무 권리도 없음** |

"쓰면 안 되는 라이선스"는 실질적으로 GPL, AGPL, 그리고 오픈소스가 아닌 것들이다. LGPL과 MPL은 "쓰면 안 되는" 게 아니라 "조건을 지키면 되는" 쪽이다.

## 대안을 찾다가: 전부 같은 코드였다

LGPL이 부담스러우니 다른 라이브러리를 찾아보기로 했다. npm registry API로 직접 조회한 결과다.

| 패키지 | 선언 라이선스 | 실제 내용물 |
|---|---|---|
| `libheif-js` | **LGPL-3.0** | libheif + libde265 (정직한 표기) |
| `heic-to` | **LGPL-3.0** | libheif 래퍼 (정직한 표기) |
| `heic-decode` | ISC | `dependencies`에 `libheif-js` → 실질 LGPL |
| `heic-convert` | ISC | `heic-decode` 경유 → 실질 LGPL |
| `heic2any` | MIT | **dist 1.35MB가 libheif 빌드. LGPL 고지 없음** |
| `@saschazar/wasm-heif` | MIT | libheif + libde265 소스로 빌드 |

브라우저용 HEIC 디코더는 **전부 libheif + libde265**다. HEVC 디코더를 처음부터 새로 짜는 건 현실적이지 않으니 당연한 결과였다. MIT 라이선스로 나온 순수 HEVC 디코더가 하나 있긴 한데(261KB WASM) 비디오 스트림 전용이라, 쓰려면 HEIF 컨테이너 파싱(item box, `hvcC`, 아이폰이 흔히 쓰는 grid/tile derived image, EXIF orientation, alpha aux item)을 직접 구현해야 한다. libheif가 하는 일의 대부분이다.

**여기서 핵심은 이거다.** MIT라고 표기된 걸 고른다고 법적 사실이 바뀌지 않는다. 고지만 사라질 뿐이다.

실제로 `heic2any`의 dist를 뜯어봤다.

```bash
$ ls -l node_modules/heic2any/dist/
-rw-r--r--  1351840  heic2any.min.js

$ strings dist/heic2any.min.js | grep -ic "libheif\|emscripten"
2

$ cat LICENSE.md | head -1
MIT License
```

1.35MB짜리 emscripten libheif 빌드를 담고 있으면서 LGPL 고지가 한 줄도 없다. 즉 **되돌아가는 게 개선이 아니라 악화**였다. 관리 가능한 LGPL 준수 과제에서, 고지가 제거된 LGPL 코드 배포로 내려가는 것이다.

## 겁주는 프레임이 만드는 오답: OR 이중 라이선스

전체 의존성 트리를 스캔해봤다. `pnpm licenses list --json`은 직접 의존성뿐 아니라 전이 의존성까지 훑는다.

약 2,000개 패키지 중 카피레프트로 잡힌 것들이다.

| 패키지 | 표기 | 실제 |
|---|---|---|
| `node-forge` | `(BSD-3-Clause OR GPL-2.0)` | **BSD-3-Clause 선택. GPL 아님** |
| `dompurify` | `(MPL-2.0 OR Apache-2.0)` | **Apache-2.0 선택. 카피레프트 아님** |
| `harmony-reflect` | `(Apache-2.0 OR MPL-1.1)` | **Apache-2.0 선택** |

**`OR`는 선택지이지 누적이 아니다.** 문자열에 "GPL-2.0"이 들어있다는 이유로 `node-forge`를 금지하면, 아무 문제 없는 걸 막느라 시간을 쓰게 된다. 반대로 `AND`로 묶인 건 둘 다 지켜야 한다.

"GPL이 보이면 무조건 금지"라는 프레임으로 판단하면 이런 오답이 나온다. SPDX 표현식 문법을 알고 봐야 한다.

## devDependencies에 있는데 1.4MB로 배포된다

이게 이번에 가장 실무적으로 값진 발견이었다.

보통 "`--prod`로 보면 배포되는 것만 나온다"고 배운다. 그런데 문제의 `libheif-js`는 **`devDependencies`에 있었다.** 그러면서 실제로는 1.4MB 청크로 브라우저에 나간다.

```
build/assets/wasm-bundle-D_epx4QE-C9fwxH_U.js   1,461.20 kB │ gzip: 517.66 kB
```

사내 공용 패키지를 소스로 소비하는 구조라 번들러가 그 패키지의 소스를 통째로 삼키는데, 이때 dev/prod 경계가 지워진다. **`--prod`로만 검사하는 정책을 세웠다면 정작 유일하게 문제되는 패키지를 놓쳤을 것이다.**

믿을 건 매니페스트 필드가 아니라 **빌드 산출물**이다.

```bash
pnpm build
grep -rl "패키지_고유_문자열" build/assets/*.js
```

이 방법으로 확인해보니 MPL로 잡혔던 것들(접근성 테스트 도구, CSS 빌드 도구)은 전부 포함된 청크 수가 0이었다. 빌드 타임에만 쓰이고 배포되지 않으니 애초에 의무가 없다.

## 고지 페이지가 94%를 놓치고 있었다

라이선스 고지 페이지를 `license-report`로 자동 생성하고 있었는데, 이 도구는 **직접 의존성만** 훑는다.

```
package.json 직접 의존성    130개 (deps 65 + devDeps 65)
생성된 report.html 행 수    131개 (= 130 + 헤더 1행)
실제 의존성 트리            2,024개
```

전체의 **94%가 고지 페이지에 나타나지 않는다.** 그리고 `libheif-js`는 사내 패키지 내부 의존성이라 정확히 여기 걸린다. 1.4MB LGPL 코드를 배포하면서 고지 페이지에는 한 줄도 없는 상태였다.

행 수가 직접 의존성 개수 + 1과 정확히 일치하는 걸로 원인을 확정할 수 있었다.

## 표기만 하면 되는가

아니다. LGPL-3.0 §4(Combined Works)는 5개 요건을 요구하는데 표기는 그중 셋이다.

| 조항 | 요구사항 | 표기로 해결 |
|---|---|---|
| §4(a) | 라이브러리 사용 사실과 LGPL 적용 사실 고지 | O |
| §4(b) | GPL + LGPL 전문 동봉 | O |
| §4(c) | 저작권 고지 표시 시 라이브러리 것도 포함 | O |
| **§4(d)** | **사용자가 수정된 라이브러리로 재결합 가능하게 할 것** | **X** |
| §4(e) | Installation Information (GPL §6 적용 시) | 웹앱은 통상 해당 없음 |

그리고 조항들 위에 붙은 **개문(chapeau)** 에 전제가 하나 더 있다. 이게 제일 놓치기 쉽다.

> "You may convey a Combined Work under terms of your choice that, taken together, effectively do not restrict modification of the portions of the Library contained in the Combined Work **and reverse engineering for debugging such modifications**, if you also do each of the following:"

**결합 저작물의 이용약관이 라이브러리 부분의 수정과 디버깅 목적 역공학을 실질적으로 제한해서는 안 된다.** 서비스 이용약관에 포괄적인 역공학 금지 조항이 있으면 §4와 충돌한다. 코드로 해결할 수 없는 항목이다.

§4(d) 관련해서는 빌드 산출물 형태를 실측해봤다. libheif가 독립 청크 하나로 분리되어 나오고, 원본 대비 99.93% 크기라(emscripten 출력이 이미 minify된 상태라 번들러가 거의 손대지 못한다) 사실상 원본 그대로 나간다. 앱 코드도 섞이지 않았다. 교체 가능성 논거에는 유리한 형태지만, 이게 §4(d)를 충족하는지는 법률 판단 영역이다.

## 고지는 패키지에? 앱에?

사내 공용 패키지가 LGPL 라이브러리를 번들하는 구조라면, 고지를 어디에 넣어야 할지가 애매하다. 답은 **둘 다인데 역할이 다르다.**

§4(a) 원문이 "with each copy of the **Combined Work**"라고 되어 있다. 의무는 **결합 저작물의 사본을 배포하는 주체**에 발생한다. 사용자가 받아가는 건 앱의 JS 번들이지 패키지가 아니다. 사내 패키지는 외부에 배포되지 않으므로 의무 주체가 아니다.

| | 공용 패키지 | 각 앱 |
|---|---|---|
| 성격 | **전파 장치** | **이행 주체** |
| 목적 | 앱이 발견할 수 있게 사실 선언 | 최종 사용자에게 고지 |
| 대상 독자 | 앱 개발자, 스캐너 도구 | 서비스 사용자 |
| 법적 의무 | 없음 (배포 안 함) | **있음 (§4 a/b/c)** |

그런데 패키지가 아무것도 선언하지 않으면 앱이 알 방법이 없다. 실제로 패키지에 `license` 필드도, `LICENSE` 파일도, README 언급도 없었다. 그래서 스캐너가 `n/a`만 뱉고 그 안의 LGPL 라이브러리는 존재조차 드러나지 않았다.

각 앱에 손으로 적어 넣을 수도 있지만, 그러면 **다음에 패키지가 새 라이브러리를 하나 더 번들할 때 모든 앱이 다시 조용히 틀린다.** 패키지가 기계가 읽을 수 있는 형태로 선언해두고(`license` 필드, `dependencies`로 이동, `THIRD-PARTY-NOTICES.md`) 앱은 전이 의존성 스캔으로 수집하는 구조여야 자동으로 따라온다.

## 정리

- **카피레프트는 소유권을 가져가지 않는다.** 조건부 허락이고, 어기면 잃는 건 내 코드가 아니라 배포할 권리다
- **의무는 사용이 아니라 배포에 걸린다.** 프론트엔드 JS는 배포다. 서버 사이드는 배포가 아니다(그래서 AGPL이 따로 있다)
- **`OR` 이중 라이선스는 유리한 쪽을 고르면 끝난다.** 문자열에 GPL이 보인다고 막으면 엉뚱한 걸 막는다
- **`dependencies` / `devDependencies` 구분은 번들러 앞에서 무의미하다.** 믿을 건 빌드 산출물 grep이다
- **npm `license` 필드는 저자의 주장일 뿐 내용물 보증이 아니다.** WASM이나 네이티브 바이너리를 품은 패키지는 직접 뜯어봐야 한다
- **자동 생성되는 고지 페이지는 무엇을 스캔하는지 확인해야 한다.** 직접 의존성만 훑는 도구가 많다
- **표기는 필요조건이지 충분조건이 아니다.** LGPL은 교체 가능성과 이용약관까지 본다

가장 크게 배운 건, "쓰면 안 되는 라이선스 목록"을 외우는 게 아니라 **배포하는가**와 **결합 범위가 어디까지인가** 두 축으로 판단하는 방법이었다. 목록을 외우면 `node-forge` 같은 걸 막고 `devDependencies`에 숨은 1.4MB를 놓친다.
