## 배경 / 계기

담당 프로젝트 하나가 다른 프론트 레포와 배포 방식이 달랐다. 다른 레포는 빌드 결과물을 S3에 올리는데, 이 레포는 Docker 이미지를 만들어 ECS에 올리고 CodeDeploy가 블루/그린으로 배포했다. 배포 한 번에 1시간이 걸리는 것도 이상해서 구조를 찾아봤다.

## 핵심 개념

### 블루/그린은 대상 그룹 두 개로 만든다

```
사용자 → ALB(로드밸런서) → 리스너(들어온 요청을 받는 창구)
                            └ 대상 그룹: 요청을 보낼 컨테이너 목록
```

핵심은 **대상 그룹이 두 개**라는 점이다.

**1단계. 새 버전(그린)을 옆에 띄운다**

```
리스너 ──→ [대상 그룹 A] 옛 버전 (사용자 100%)
           [대상 그룹 B] 새 버전 (트래픽 없음)  ← 새로 띄움
```

새 버전이 헬스체크를 통과할 때까지 기다린다. 실패하면 여기서 중단된다. 사용자는 아무 영향을 받지 않는다.

**2단계. 리스너가 보는 대상 그룹을 바꾼다**

```
리스너 ──→ [대상 그룹 B] 새 버전 (사용자 100%)
           [대상 그룹 A] 옛 버전 (트래픽 없음, 아직 살아 있음)
```

이 순간이 실제 배포 시점이다. `CodeDeployDefault.ECSAllAtOnce` 설정이면 한 번에 전부 넘어간다.

**3단계. 옛 버전을 한동안 남겨 둔다**

배포 1건에 1시간이 걸리던 이유가 이 대기 시간이었다. 이 사이에 문제가 발견되면 **리스너만 되돌리면 롤백이 끝난다.** 다시 빌드하거나 컨테이너를 띄울 필요가 없어서 수십 초면 된다. 실제로 배포 내역에 `CodeDeploy 롤백` 기록이 남아 있었고, 모두 같은 날 재배포로 마무리돼 있었다.

대기가 끝나면 옛 컨테이너를 종료한다.

### 다른 배포 방식과 비교

| 방식 | 동작 | 트레이드오프 |
|------|------|--------------|
| 블루/그린 | 새 버전 전체를 띄운 뒤 한 번에 전환 | 롤백이 빠름. 배포 중 자원이 2배 필요 |
| 롤링 (ECS 기본) | 컨테이너를 하나씩 교체 | 자원을 덜 씀. 교체 중 두 버전이 섞임, 롤백 느림 |
| 카나리 | 10%만 먼저 넘기고 관찰 후 나머지 | 위험이 가장 작음. 설정이 복잡 |

## ECS 배포와 S3 + CloudFront 배포의 차이

무엇이 교체되는지가 다르다.

```
ECS:   실행 중인 프로그램(컨테이너)을 통째로 교체
       → 로드밸런서가 전환 시점을 관리. 헬스체크로 검증 가능

S3+CF: 창고의 파일을 덮어쓰기
       → 프로그램이 없으니 헬스체크할 대상도 없음. 파일이 곧 서비스
```

| | ECS | S3 + CloudFront |
|---|------|------------------|
| 배포되는 것 | Docker 이미지 | 정적 파일 |
| 걸리는 시간 | 수십 분 | 1~2분 |
| 롤백 | 리스너를 되돌리면 즉시 | 이전 결과물을 다시 업로드 |
| 실패 감지 | 헬스체크 실패 시 자동 중단 | 없음. 잘못 올려도 그대로 서비스 |
| 서버 실행 코드 | 있음 (SSR, API 라우트 가능) | 없음 |
| 비용 | 서버를 계속 켜 둠 | 요청과 용량만큼 |

### 정적 배포에서 캐시를 따로 다루는 이유

CloudFront는 파일을 전 세계에 복사해 두고 나눠준다. S3에 새로 올려도 예전 파일이 계속 나갈 수 있다. 그래서 정적 배포 파이프라인에는 늘 이 두 줄이 붙는다.

```groovy
// index.html 은 캐시하지 않도록 지정
s3Upload(bucket: bucketName, file: 'build/index.html',
         cacheControl: 'max-age=0, no-cache, no-store, must-revalidate')

// CloudFront 에 캐시된 사본 제거
cfInvalidate(distribution: cloudfrontId, paths: ["/index.html"])
```

JS와 CSS는 파일명에 해시가 붙어(`main.c2b33a.js`) 내용이 바뀌면 이름도 바뀌므로 캐시돼도 괜찮다. 이름이 고정된 `index.html`만 따로 다루면 된다. ECS에는 이런 고민이 없다. 서버가 매번 응답을 만들기 때문이다.

## 왜 이 방법인가

이 레포는 ECS 구조지만, 코드를 열어보니 `getServerSideProps`가 전부 빈 값을 반환하고 있었다. 서버에서 실제로 하는 일이 없는, 사실상 정적 사이트를 서버로 띄워 둔 상태였다.

그래도 이번에 정적 배포로 옮기지는 않았다. 옮기려면 export 설정 변경, 동적 경로를 파일로 연결하는 CloudFront 규칙, 로드밸런서에서 CloudFront로 주소 이전까지 따라온다. 운영 중인 서비스라 배포가 막힌 상황에서 같이 할 일은 아니었다.

## 정리

- 블루/그린의 본질은 **대상 그룹 두 개 사이에서 리스너가 바라보는 곳을 바꾸는 것**이다. 그래서 롤백이 빠르다.
- 배포에 한참 걸린다면 대부분 "옛 버전을 남겨 두는 대기 시간"이다. 멈춘 게 아니다.
- ECS는 프로그램을 교체하고, S3+CloudFront는 파일을 덮어쓴다. 헬스체크와 캐시 고민이 여기서 갈린다.
- 구조는 ECS인데 서버가 하는 일이 없을 수 있다. 다만 호스팅 방식을 바꾸는 건 배포 도구를 바꾸는 것과 별개의 작업이다.
