## 배경 / 계기

CloudFront 뒤에서 이미지 리사이즈를 처리하는 Lambda 스택을 CDK로 배포해 쓰고 있었다. AWS 솔루션 템플릿을 포크해서 쓰는 구조라 런타임이 `NODEJS_20_X`로 박혀 있었다.

Lambda의 managed runtime deprecation은 단계가 나뉘어 있다.

| 단계 | 시점 | 무슨 일이 생기나 |
|------|------|----------------|
| deprecated | 2026-04-30 | 보안 패치와 기술 지원이 끊긴다. 함수는 계속 돈다 |
| 함수 생성 차단 | 이후 | 그 런타임으로 새 함수를 만들 수 없다 |
| 함수 업데이트 차단 | 2027-03-03 | 기존 함수의 코드·설정 변경이 거부된다 |

당장 장애가 나는 건 아니다. 문제는 마지막 단계다. **업데이트가 차단되면 그 스택에 CDK 배포 자체가 불가능해진다.** 이미지 핸들러 코드를 한 줄 고치는 것도 못 하게 된다. 그때 가서 런타임을 올리려면 "배포가 막힌 상태에서 배포로 고쳐야 하는" 상황이 되므로, 그 전에 미리 올려 배포 경로를 열어두는 작업이다.

## 무엇을 바꿨나

먼저 레포 전체에서 런타임 선언을 훑었다.

```bash
grep -rn "NODEJS_2[0-9]_X" --include="*.ts" source/ | grep -v node_modules
```

- 이미지 처리 Lambda, 커스텀 리소스 Lambda: `NODEJS_20_X` → `NODEJS_22_X`
- 메트릭 Lambda: 이미 22였다
- API Gateway / S3 Object Lambda 아키텍처 쪽 함수: CloudFront Function(`JS_2_0`)이라 대상이 아니다

```typescript
// before
runtime: Runtime.NODEJS_20_X,

// after
runtime: Runtime.NODEJS_22_X,
```

CloudFront Function은 Lambda가 아니라 별도 런타임이다. 이름만 보고 같이 올리려 하면 안 된다.

## 왜 24가 아니라 22인가

Jenkins 쪽은 같은 시기에 24로 올렸는데 여기는 22로 갔다. 이유는 하나씩 확인 가능한 것들이었다.

**1. 쓰고 있는 CDK 버전에 24가 없다.** 이건 문서를 찾을 것도 없이 설치된 타입 정의를 보면 된다.

```bash
grep -o "NODEJS_2[0-9]_X" node_modules/aws-cdk-lib/aws-lambda/lib/runtime.d.ts | sort -u
# NODEJS_20_X
# NODEJS_22_X
```

`Runtime.NODEJS_24_X`가 없다. 24로 가려면 aws-cdk-lib 업그레이드가 동반되고, 그러면 스택 전체의 합성 결과가 바뀌어 PR 성격이 달라진다.

**2. 업스트림도 22다.** 포크해 쓰는 원본 솔루션이 최신 릴리스에서 nodejs22로 갔다. 업스트림을 따라가면 나중에 태그를 머지할 때 충돌이 줄어든다.

**3. 런타임 지원 범위.** Lambda가 관리형으로 제공하는 Node 런타임 중 당시 최신이 22였다.

Node 22는 2027-04-30 EOL이라 언젠가 또 해야 한다. 다만 그 시점에는 CDK도 24를 지원할 테니 그때 CDK 업그레이드와 함께 가는 편이 낫다고 봤다.

## 런타임 상수만 바꾸면 끝이 아니다

처음엔 `NODEJS_22_X` 두 줄만 바꿔서 올렸다. 리뷰에서 지적받은 게 있다. **Lambda 런타임만 22로 올리고 개발 환경은 20에 남아 있다는 것.**

이 레포는 CI 배포가 없고 `npm run cdk-deploy`로 로컬에서 배포가 나간다. 즉 개발자 로컬이 곧 배포 환경이다. 로컬 Node 20에서 빌드한 산출물이 Lambda의 Node 22에 올라가는 구조라, 버전 정합성이 형식적인 문제가 아니었다.

- `.nvmrc`: 20 → 22
- `@types/node`: 패키지 7개 전부 20.x → 22.20.1

`@types/node`가 20.x로 남아 있으면 22에 있는 API를 타입 수준에서 모르거나, 반대로 20 기준 시그니처로 검사하게 된다. 지적받은 두 곳 외에도 유틸, 커스텀 리소스, 메트릭, 배포 헬퍼까지 20.x가 남아 있어서 레포 안에서 버전이 섞이지 않도록 함께 올렸다. 원래 캐럿 없이 고정돼 있던 패키지는 고정을 유지했다.

TypeScript 버전은 그대로 뒀다. 함께 올리면 이 PR이 "런타임 업그레이드"가 아니라 "툴체인 업그레이드"가 된다.

검증은 6개 패키지 전부 `tsc --noEmit`으로 했다. `lib: es2018` + `strict`에 `skipLibCheck`가 없는 패키지가 가장 위험했는데 이상 없었다.

## 걸린 것들

**스냅샷 테스트.** CDK 스냅샷에 런타임 문자열이 그대로 들어 있어서 `nodejs20.x` → `nodejs22.x`로 갱신이 필요했다. 합성 결과를 통째로 비교하는 테스트라 런타임 한 줄만 바꿔도 깨진다.

**package-lock의 착시.** `source/constructs/package-lock.json`이 1만 줄 넘게 바뀐 것으로 나와서 처음엔 뭔가 크게 잘못된 줄 알았다. 실제로는 대부분 npm의 키 재정렬이었다. 435개 패키지 중 의미상 바뀐 건 `@types/node`의 버전·resolved·integrity, 그리고 형제 패키지의 stale한 버전 표기가 실제 값으로 보정된 것뿐이었고 의존성 추가나 삭제는 없었다. diff 크기에 놀라기 전에 무엇이 바뀌었는지 세어보는 편이 낫다.

## 왜 이 방법인가

런타임 상수만 바꾸는 두 줄짜리 PR로 끝낼 수도 있었다. 실제로 배포도 됐을 것이다. 그렇게 하지 않은 이유는 그 상태가 "Lambda는 22, 로컬은 20"이라는 새로운 드리프트를 만들기 때문이다. 지금 겪고 있는 문제가 정확히 그 드리프트가 오래 방치된 결과였다.

반대로 CDK까지 같이 올려 24로 가는 방법도 있었지만, 런타임 업그레이드와 프레임워크 업그레이드는 실패했을 때 원인을 가르는 방식이 다르다. 한 PR에 섞으면 배포가 깨졌을 때 어느 쪽인지 알기 어렵다.

## 정리

- Lambda 런타임 deprecation의 진짜 데드라인은 "함수 업데이트 차단" 시점이다. 그때가 되면 배포로 고치는 것 자체가 막히므로 그 전에 올려야 한다.
- 런타임 선언은 `grep -rn "NODEJS_2[0-9]_X"`로 레포 전체를 훑는다. CloudFront Function은 Lambda 런타임이 아니라 대상이 아니다.
- CDK가 특정 런타임을 지원하는지는 설치된 `node_modules/aws-cdk-lib/aws-lambda/lib/runtime.d.ts`를 보면 바로 확인된다.
- 런타임 상수만 올리면 로컬과 배포 환경 사이에 새 드리프트가 생긴다. `.nvmrc`와 `@types/node`까지 같이 맞춘다. 특히 로컬에서 배포하는 레포라면 로컬이 곧 배포 환경이다.
- package-lock의 diff 크기는 대부분 키 재정렬이다. 놀라기 전에 의미 있는 변경만 세어본다.
