## 문제 상황

"CodeDeploy가 멈춰서 Jenkins로 옮겨야 한다"는 요청을 받았다. 운영툴 웹앱의 배포가 안 되니 배포 도구를 갈아타자는 이야기였다.

레포를 열어보니 다른 프론트 프로젝트와 구조가 달랐다. 빌드 결과물을 S3에 올리는 방식이 아니라 `Dockerfile`, `taskdef.json`, `appspec.yaml`이 있는 ECS 배포였다. 그래서 Jenkins에서 CodeDeploy를 호출하는 파이프라인을 짜기 시작했다.

그런데 실패한 배포 기록을 열어보니 이상했다.

```
Deployment d-XXXXXXXXX failed.
Error code: INTERNAL_ERROR
Error message: Internal error occurred during deployment.
Rollback message: No auto rollback triggered since deployment terminated
                  before adding any instances
```

32초 만에, 컨테이너를 하나도 띄우지 못하고 끝났다.

## 원인 분석

### 1. dev는 2년 넘게 실패하고 있었다

CodeDeploy 배포 그룹의 **배포 내역** 화면을 열었다. 한 페이지에 보이는 20건이 전부 실패였고, 가장 오래된 것이 2년 전이었다. 모두 시작 시간과 종료 시간이 같은 분이었다.

"최근에 뭔가 삭제돼서 멈췄다"가 아니라 **원래부터 한 번도 성공한 적 없는 상태**였다. 그동안 dev 실패는 넘기고 운영에만 배포해 온 것이다.

### 2. 운영 CodeDeploy는 멀쩡했다

그렇다면 운영은 어떨까. 운영 배포 그룹의 내역은 반대였다. 2년치 기록이 대부분 성공이었고, 마지막 성공이 11개월 전이었다. 중간의 실패 몇 건도 자동 롤백 후 같은 날 다시 성공해 있었다.

즉 **CodeDeploy는 멈춘 적이 없었다.**

### 3. 파이프라인 화면을 보니 빨간 칸은 맨 앞이었다

여기서 CodePipeline 전체 화면을 열었다. 네 칸 중 빨간 것은 하나뿐이었다.

```
[Source]  [Build]  [approval]  [Deploy]
  ✗         ✓          ✓          ✓
```

Source 칸의 상세 정보에 원인이 그대로 적혀 있었다.

```
No Connection found with ARN:
arn:aws:codestar-connections:ap-northeast-2:123456789012:connection/xxxxxxxx-...
```

GitHub에서 코드를 가져오는 연결이 **삭제돼 있었다.** 실행 시간도 1초였다. 코드를 가져오지 못했으니 뒤의 Build도 Deploy도 애초에 시작되지 않았고, 사람들 눈에는 "배포가 안 된다"로만 보인 것이다.

## 해결 방법

연결을 새로 만들고 Source 작업에 다시 지정하면 된다. Build, 승인, Deploy 설정은 손댈 필요가 없다.

1. **개발자 도구 → 설정 → 연결**에서 상태가 "사용 가능"인 GitHub 연결이 있는지 확인. 다른 파이프라인이 쓰는 연결이 있으면 그대로 재사용한다.
2. 없으면 연결을 새로 만든다. GitHub 조직에 AWS Connector 앱 설치가 필요할 수 있고, 이때는 조직 관리자 승인이 필요하다.
3. 파이프라인 편집 → Source 작업에서 연결, 저장소, 브랜치를 지정한다. **출력 아티팩트 이름은 기존 값 그대로** 둔다. 뒤의 Build 단계가 그 이름으로 결과물을 받기 때문이다.

연결 생성은 IAM 권한이 필요해서 결국 권한 있는 분께 요청했다.

## 왜 이 방법인가

Jenkins로 옮기는 작업을 절반쯤 진행한 뒤에야 이 결론에 도달했다. 그 과정에서 빌드 에이전트에 docker가 없다는 사실, 아티팩트 버킷 정책, IAM 권한 부족까지 줄줄이 마주쳤다. 전부 "배포 도구를 갈아탄다"는 전제 때문에 생긴 비용이었다.

연결 하나를 복구하면 기존 파이프라인이 그대로 살아난다. 검증된 경로고, 운영 인프라를 건드리지 않는다. 배포 도구를 바꾸는 것보다 압도적으로 싸다.

## 정리

- 배포 실패를 들었을 때 **파이프라인 전체 화면에서 어느 칸이 빨간지부터 확인**한다. 증상을 전해 들은 이름(여기서는 CodeDeploy)이 원인이라는 보장이 없다.
- 배포 **내역 목록**은 좋은 진단 도구다. 실패가 언제부터인지 보면 "최근에 깨졌다"와 "원래 안 됐다"를 구분할 수 있다.
- 배포 시간이 1초, 30초처럼 비정상적으로 짧으면 실제 작업 전에 막힌 것이다. 준비 단계나 권한, 연결을 먼저 의심한다.
- 개발 환경 배포가 조용히 실패하고 있어도 아무도 모를 수 있다. 운영만 배포하는 습관이 생기면 더욱 그렇다.
