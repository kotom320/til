## 배경 / 계기

백엔드가 API 스펙을 바꾼 뒤 OpenAPI 타입을 재생성했더니 CI에서 이런 에러가 났다.

```bash
error TS2741: Property 'brandId' is missing in type '{ name: string; visible: boolean; ... }'
but required in type '{ name: string; brandId: number; visible: boolean; ... }'.
```

처음엔 "서버가 필드를 추가해도 프론트에서 안 쓰면 그만 아닌가?" 싶었다. 내가 알던 상식은 이랬다.

- 서버가 필드를 **추가**하면: 프론트는 안 쓰면 그만
- 프론트는 필수로 선언했는데 서버가 **안 주면**: 화면에서 에러

그런데 에러가 난 곳을 열어보니 GET 응답이 아니라 POST/PUT의 **request body**였다. 상식이 틀린 게 아니라, 그 상식은 **응답 방향**에만 해당하는 이야기였다.

## 핵심 개념

### 전제: 타입은 런타임에 없다

TypeScript 타입은 컴파일 시점에만 존재한다. 응답을 `zod.parse` 같은 런타임 검증으로 거르지 않는 한, 서버가 **실제로** 무엇을 보냈는지는 타입 체크가 알 수 없다. 그래서 응답 쪽 문제는 대부분 런타임에서야 드러난다.

### 기준은 HTTP 메서드가 아니라 데이터가 흐르는 방향

| 방향 | 해당 위치 | 서버가 필수 필드를 추가하면 |
|---|---|---|
| 프론트 → 서버 | body, query, path, header | 프론트가 채워야 함. 안 채우면 **컴파일 에러** |
| 서버 → 프론트 | 응답 body | 안 쓰면 그만. **무해** |

요청에서는 서버가 받는 쪽이다. 받는 쪽이 "필수"라고 하면 보내는 쪽이 반드시 채워야 한다. 응답에서는 프론트가 받는 쪽이라 관계가 뒤집힌다.

GET이라고 안전한 것도 아니다. `openapi-fetch`는 `required: true`인 query 파라미터를 `params.query`에 강제하므로, 서버가 GET에 필수 query를 추가해도 똑같이 TS2741이 난다. path 파라미터는 OpenAPI 규칙상 항상 필수다. GET은 보내는 값이 대개 옵셔널 query라서 체감상 덜 걸릴 뿐이다.

### 응답(GET) 쪽 상세

**1-a. 필수로 선언했는데 서버가 안 주는 경우**

컴파일은 통과한다. 런타임 값이 `undefined`일 뿐이고, 결과는 **그 값을 어떻게 쓰느냐**에 따라 갈린다.

| 사용 방식 | 결과 |
|---|---|
| `{data.name}` JSX 렌더 | 에러 없이 빈칸 (조용한 버그) |
| `data.name.split(',')` | `TypeError` → 화면 깨짐 |
| `data.user.name` (중첩 객체 없음) | `TypeError` |
| `dayjs(data.createdAt)` | 크래시는 없지만 **현재 시각**이 표시됨 |
| `data.list.map(...)` | `TypeError` |

"화면에서 에러가 난다"보다는 "언제 터질지 모르는 상태"가 정확하다. 차라리 크래시가 나면 빨리 발견되는데, 빈칸이나 엉뚱한 값으로 넘어가는 쪽이 더 위험하다.

**1-b. 옵셔널로 선언했는데 서버가 안 주는 경우**

TS가 `?.`, `??`, 조건 분기 같은 `undefined` 처리를 강제한다. 그 처리를 이미 해뒀으니 런타임에도 안전하다. 옵셔널이 원래 노리는 효과가 이것이다.

단, **`null`은 주의**해야 한다. 스펙에 `nullable`이 빠져 있는데 서버가 `null`을 보내면 타입은 `string | undefined`인데 실제 값은 `null`이다.

```ts
type TItem = { name?: string };
const data = { name: null } as unknown as TItem; // 서버가 실제로 보낸 값

data.name ?? '-';              // '-'  (null 도 걸러줌)
data.name?.length;             // undefined (안전)
data.name === undefined;       // false  ← null 을 놓침
const { name = '-' } = data;   // name 은 null  ← 기본값이 적용되지 않음
```

**2. 선언하지 않았는데 서버가 주는 경우**

컴파일도 런타임도 문제없다. 아무도 읽지 않는 키가 객체에 하나 더 있을 뿐이다. 예외는 하나다. 응답을 그대로 요청에 재사용할 때다.

```ts
const detail = await getPromotion(id);   // 타입에 없는 필드도 실제로는 들어 있음

await putPromotion({
  ...detail,          // 타입에 없던 필드까지 그대로 전송됨
  name: '수정된 이름',
});
```

TS의 초과 속성 검사(excess property check)는 **객체 리터럴에 직접 쓴 키**만 잡는다. 스프레드로 들어온 키는 통과한다. 서버가 모르는 필드를 거부하도록 설정돼 있으면 여기서 400이 난다.

## 예시 코드

에러가 났던 코드는 이런 모양이었다. 서버가 요청 DTO에 `brandId`를 필수로 추가했고, 타입을 재생성하자 바로 잡혔다.

```ts
const postPopup = $api.useMutation('post', '/promotions/popup');

postPopup.mutateAsync({
  body: {
    name: form.name,
    visible: form.visible,
    // brandId 누락 → TS2741
  },
});
```

이 에러는 배포 전에 계약 위반을 잡아준 것이다. 타입 체크가 없었다면 `brandId` 없이 요청이 나가서 400을 받거나 `null`로 저장됐을 것이다.

## 왜 이렇게 정리해 두는가

OpenAPI에서 타입을 생성해 쓰면 "서버 스펙 변경 = 타입 변경"이라서, 어떤 변경이 컴파일에서 잡히고 어떤 변경이 런타임으로 새는지 구분할 수 있어야 한다.

- 스펙에서 응답 필드를 **지우면** 재생성 후 쓰던 곳이 컴파일 에러로 잡힌다.
- 요청에 필수 필드가 **추가되면** 컴파일 에러로 잡힌다.
- 런타임으로 새는 건 **스펙과 실제 응답이 다를 때**뿐이다. 스펙엔 있다고 해놓고 실제로 안 주거나, `nullable` 표기가 빠진 경우. 타입 체크로는 막을 수 없으니 이건 런타임 검증이나 방어 코드로만 대응할 수 있다.

## 한 장 요약

| 상황 | 컴파일 | 런타임 |
|---|---|---|
| 응답: 필수 선언, 서버가 안 줌 | 통과 | 사용 방식에 따라 크래시 / 빈칸 / 엉뚱한 값 |
| 응답: 옵셔널 선언, 서버가 안 줌 | `undefined` 처리 강제 | 안전 (`null`만 주의) |
| 응답: 미선언, 서버가 줌 | 통과 | 무해 (요청으로 재사용할 때만 주의) |
| 요청: 서버가 필수 필드 추가 | **에러** | 안 보내면 400 |

## 정리

응답은 "서버가 주는 만큼만 믿고", 요청은 "서버가 요구하는 건 다 채운다". 기준은 메서드가 아니라 데이터가 흐르는 방향이다.
